# Phase 7 implementation plan: hot-wallet accounting

**Status:** Opt-in implementation present; focused runtime verification passed on disposable databases; comprehensive independent release gates remain open. See [measured evidence](phase6/phase7-verification.md). See [implementation and limits](phase6/phase7-implementation.md), [work tracking](phase6/phase7-progress.md), and [independent testing brief](phase6/phase7-testing-brief.md). The acceptance gates below remain open until executed. Split/merge mutations remain unsupported because the required golden evidence is absent.

## Design decision

Start with `(wallet, condition_id)` as the unit of work on the wallet's existing PostgreSQL shard. A buy or sell depends on prior shares and average cost for one token. A redemption with no token examines every eligible open position in its condition, so it must see earlier events for the entire condition. Different conditions can compute independently under the current rules. Missing or otherwise unclassifiable dependencies use the serial path. A wallet concentrated in a single condition will still process that condition serially.

Keep one coordinator per wallet. It acquires the existing wallet advisory lock on the owning shard, locks the wallet total row, and takes a bounded batch of source events and relevant position state. A bounded process pool computes condition results from those inputs without database connections or publication rights. The coordinator waits for every condition, validates coverage, and writes positions, ledger, rejects, checkpoints, totals and applied progress in one PostgreSQL transaction on the lock connection. On failure it discards the uncommitted batch, and the next owner starts from the last committed cursor. An old worker or a delayed process result cannot publish through a replacement database connection. Start with short batches and a configurable pool size shared within a worker process. Measure lock hold time and CPU contention before widening concurrency.

Within a condition, preserve the applicable serial order. Current incremental processing uses `api_order` and full replay uses `(event_time, api_order)` after excluding superseded observations. Establish equivalence on timestamp ties and out-of-order events within a single delivered batch before switching paths. The coordinator applies PnL deltas in the serial reference order with the same Decimal precision. Adding pre-summed condition totals can change results because Decimal addition at fixed precision is order dependent. Advance the wallet cursor only when the complete selected batch has been applied, including the disposition of rejected and unsupported events. Account for superseded orders when checking completeness. API and WebSocket readers continue to see a committed wallet snapshot. Notify them only after commit.

## Data flow and release invariants

| Step | Required behavior |
| --- | --- |
| Route and ingest | Normalize and validate the wallet, resolve its owning shard, and verify shard identity before processing. Commit source events, deduplication and supersession, ingestion progress, and any correction marker together. Reject a wrong-wallet payload or wrong-shard write without advancing progress. |
| Select and compute | Bind every work item and result to its wallet, shard, condition, and coordinator batch. Read the source range, correction boundaries and starting positions under the wallet's accounting lock. Require exactly one disposition per selected active event and validate ownership and range on every returned effect. Roll back for missing, duplicate, stale, or misrouted results. A child process cannot write to PostgreSQL. |
| Publish and recover | Publish all derived changes and both accounting progress fields in one transaction. Clear a correction marker only when its replay has committed with that state. After a lost connection or ambiguous commit, reacquire ownership and read durable progress before deciding what to retry. Never reuse a result from the failed attempt. Keep source identities stable so retries cannot add a second economic effect. |
| Serve | Read wallet positions, totals and accounting freshness from the same committed wallet snapshot. During backlog or correction, label older committed results as behind. Compare before/during/after responses to make sure readers never see a partly published correction. Shard failure must return explicit unavailability, and any cross-shard response with incomplete coverage must mark it or fail. Price freshness is tracked separately because shared marks can come from a separate snapshot. |
| Reconnect | Send notifications after commit. Treat a notification as a signal to read committed state. A WebSocket reconnect or refresh rereads current state even when a worker stopped after commit and before sending the notification. Test a correction that changes PnL without advancing `api_order`, so freshness and refresh do not rely solely on a higher cursor. |

Release requires tracing the same seeded events from source identity through ingestion progress, condition results, committed ledger and balances, and REST/WebSocket output. Interleave two wallets on the same shard and a third on the other shard. Inject an overlapping worker, duplicate delivery, a correction during processing, a lost or delayed result, and database failure. Compare each wallet independently with the serial reference and check that the other wallets' economic state and progress stay unchanged. Keep the serial path as the default until these checks and the accounting parity gate pass, regardless of throughput.

## Concurrency failure cases

These cases are part of the implementation and release checks. Seeded schedule tests should use barriers at transaction and task boundaries to force the intended race. Supplement them with repeatable randomized interleavings and compare each completed run with serial replay.

| Failure or race | Safeguard and required evidence |
| --- | --- |
| Connection replaced between transactions or ownership lost during compute | Require the publish transaction to hold the wallet fence on its own physical database session. Bind inputs and results to that attempt. Test backend termination both between transactions and after inputs are captured. If a pool reconnects, the old attempt has to abort. The replacement owner must be able to progress, and the original attempt must make zero changes. |
| Ingestion, serial rebuild, and parallel projection overlap | Trace normal ingestion, backfill, supersession and manual rebuild entry points. Route every source or derived-state mutation through the same wallet serialization protocol with a documented lock order. If a source change waits behind publication, it must atomically mark the next correction after the lock is released. Test deadlock or timeout rollback and retry from fresh state, including overlap with checkpoint maintenance. |
| Tasks finish out of order or return inconsistent output | Match every response to its exact attempt, input event identities, and declared condition. Verify complete coverage, position keys, and expected output cardinality, including legitimate multi-leg events. Merge effects in reference order. Test reordered, duplicate, malformed, timed-out, and late results. Partial completion must leave the wallet cursor and financial state unchanged. |
| Chained corrections, supersession and cursor gaps | Distinguish ingestion's high-water mark, projection coverage, and time-ordered replay boundaries. An observed maximum is insufficient evidence that earlier eligible events were handled. Test overlapping late events, supersession across a checkpoint boundary, a replacement changing dependency keys, and superseded orders at the end of a range. Compare partial replay with full rebuild, including unsupported counts reconstructed from active source events and stale ledger/reject rows removed by replay. |
| Crash before, during, or after commit | Inject failure during derived writes, immediately before commit, and after the server commits but before acknowledgement or notification. Restart with a new owner and confirm there is either one complete publication or a clean retry. A failed or uncertain attempt cannot reuse its in-memory effects. |
| An earlier WebSocket read finishes after a newer one | Order wallet snapshots by a durable publication revision that advances with accounting commits, including corrections at the same applied order. Suppress older snapshots for the same subscription, including overlap between initial snapshot and notifications. Exercise lost, duplicate, and reordered notifications and reconnect while publishing. Check accounting freshness separately from price freshness. |
| Slow or failing wallet exhausts shared capacity | Bound executor queue depth, per-wallet batch size, lock/statement duration, and concurrent database sessions. Use bounded retries for transient errors and surface repeated failures with the wallet and committed progress. Test that a hung task or hot wallet does not starve another wallet and that rollback releases locks and process slots. |
| Old and new processes coexist during rollout or rollback | Use additive schema and version checkpoint formats. Define which versions may write each format. Quiesce write paths during any incompatible transition, then verify that serial fallback can read or rebuild the last committed state without skipping events or reverting new accounting semantics. Exercise both rollout and switch-back after an interrupted correction. |

## Implementation sequence

1. [ ] **Establish the correctness and performance baseline.** Use Phase 6's serial projector and `scripts/verify_rebuild.py` as complementary references. Compare economic rows by stable keys and fields, excluding generated IDs and timestamps. Inspect representative wallets for events per condition, including a wallet with one dominant condition. The current synthetic scale benchmark assigns one condition per wallet. Keep that case as a control and add seeded fixtures with interleaved conditions, competing redeem candidates, same-second ties and corrections that alter later outcomes. Resolve any demonstrated ordering mismatch between incremental and full rebuild in a discrete change before using it as a parity gate. Record baseline timings only when the testing hold is lifted.
2. [ ] **Separate computation from persistence in `app/accounting/projector.py`.** Reuse `apply_event` in `app/accounting/engine.py`. Extract the deterministic condition calculation and a coordinator-owned write path, initially with a serial executor. Pass typed inputs and return ordered event effects, resulting positions and rejects. Keep `catch_up_wallet` and `recompute_wallet` compatible with worker and maintenance callers. Load and upsert the touched positions in batches. Compare against the original path before introducing concurrency, so database batching and process-level parallelism can be measured separately.
3. [ ] **Enable opt-in concurrency for one wallet.** Integrate a reusable, bounded process pool with `app/worker.py`. Assign eligible condition work to the pool, retaining serial handling where dependencies cannot be classified. Use a per-wallet allowlist or equivalent opt-in at launch. Keep the coordinator transaction and ownership on the same connection, cap in-flight work, and log when the serial fallback is used. If computation times out or a process dies, roll back the batch before retrying. No condition task advances its own durable cursor independently of the wallet commit.
4. [ ] **Add correction-aware condition checkpoints.** Design an additive migration for checkpoint state keyed by wallet and condition, including its replay boundary and format version. Update shard guards and shard initialization/verification and backups where new tables require it. Store the earliest invalidated boundary per affected condition in the same transaction as source ingestion. For an enrichment supersession, consider both the replaced and replacement rows, including their original ordering keys. For a correction, restore the affected condition from a checkpoint strictly before the dirty boundary and replay its active events up to the chosen wallet boundary. Leave unrelated position histories intact. Reconstruct wallet aggregates from a valid wallet aggregate checkpoint before the dirty boundary and fold the affected suffix's ledger deltas in reference order, including unchanged conditions. Define counts using the same rules as full replay. Report condition events reapplied and global rows read for aggregation separately. Use the wallet replay path for missing or incompatible checkpoint state, unclassified dependencies or any case where cursor and aggregate consistency cannot be established. Keep Phase 6 checkpoints compatible or invalidate and rebuild them before a switch to the legacy projector.
5. [ ] **Resolve the split/merge accounting boundary.** Trace real split and merge transactions through source activity, Polygon logs and balance changes. Establish affected tokens, collateral and parent collection behavior, supported event shapes, cost allocation, realized PnL and duplicate handling. Require explicit golden examples with before/after balances and ledger effects. Only implement a supported shape once those rules are established. Apply verified condition-local multi-position effects in one transaction and design stable per-leg ledger identity before emitting more than one ledger row per source event. Add new accounting rules to both the serial and parallel paths before enabling those event shapes, so disabling concurrency preserves their economic treatment. Retain unsupported cases in the raw store with an explicit accounting disposition. Hold wallet-wide or multi-condition mutations on the serial path until their semantics and lock/publication rules are independently established.
6. [ ] **Verify, measure and roll out locally.** After the testing hold is lifted, complete the relevant Phase 6 release checks, then run the Phase 7 gates below. Compare serial execution, batching with one process, and parallel execution on identical seeded data. Enable the path for one scratch wallet first. Verify disable/restart behavior after a committed batch and after an interrupted correction. Give Antigravity the independent test brief only after Codex has implemented and verified the changes and testing is authorized.

## Acceptance criteria

| Gate | Evidence required |
| --- | --- |
| Real parallel execution | Show at least two condition tasks for the same wallet executing concurrently. Exercise a single-condition control and show how that case is reported. |
| Accounting parity | Serial full rebuild and Phase 7 agree on positions, average costs, ledger deltas, realized PnL, counts, rejects and applied progress. Cover tokenless redemptions with zero, one and multiple eligible positions, timestamp ties, duplicate delivery, late events and applied-event supersession. Check any newly supported split/merge shapes against independently derived expected balances and cash effects in addition to full replay. |
| Atomic publication and recovery | Interrupt a compute task, the coordinator and its PostgreSQL connection at points before and during publication. Retry, including after a commit with an ambiguous client outcome. Verify no stale publisher, skipped events, duplicate economic effects, partial wallet view or regressions in shard isolation. Check REST and WebSocket views around a correction. |
| Bounded correction cost | Show a condition-local correction evaluates fewer position events than full-wallet replay. Record aggregation rows scanned, checkpoint bytes, transaction duration and before/after reconstruction results. An aggregate scan can still be linear in the wallet suffix. Measure it explicitly. |
| Performance and compatibility | Measure throughput, correction latency, lock duration, API p95, peak memory and disk footprint for a diverse hot wallet and a mostly single-condition wallet. Use repeated runs on the same machine and dataset, report variability, and enable by default only if improvement is reproducible without material regression in the control or existing cross-wallet workload. Verify existing data, migrations, shard restore and the serial fallback. |

Live shard rebalancing, redundant proxies, cloud deployment, off-machine backup automation, external queues, and a database change remain separate projects. PostgreSQL already provides the ownership and atomic commit needed for the initial design.

The [code assessment](phase6/phase7-accounting-assessment.md) documents the dependencies. Existing [Phase 6 measurements](phase6/measurements.md) motivate the work and use an earlier build. Phase 7 performance and correctness require fresh evidence.
